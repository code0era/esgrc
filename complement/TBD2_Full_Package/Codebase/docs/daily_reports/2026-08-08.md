### PR #16 - Registry key bug: all 7 new modules would have failed

Found by auditing each module's `output_file_patterns` against its actual script outputs
rather than reading the JSON:

Every module added on 6-7 Aug shipped patterns whose **keys** still named "shared":

```json
"output_file_patterns": {
  "metrics_summary_shared.txt": "metrics_summary_enterprise_*.txt"
}
```

The values were correctly retokenized. The keys were not. The existing test looked at values,
so it passed. A run would have silently produced the right files and then failed the
provenance check because no key matched.

Also found in the same PR: **Enterprise reference data was missing from the repo.** The
cleanup on 6 Aug deleted `Enterprise/reference_data/` entirely. The cause was my own error:
`Remove-Item ENTERPRISE` on a case-insensitive filesystem deleted `Enterprise/` while I
intended the wrongly-cased directory the script generator had briefly created. The generator
then recreated only `analytics_scripts/`. Not fatal at runtime (scripts read from R2), but a
fresh clone could not seed Enterprise. Restored byte-identical, BOM-free, `module_id ETPR_001`.

Added per-module registry contract tests so neither class of bug can recur silently.

### PR #17 - Failure-mode tests

Every analytics bug found in August produced a complete report with wrong content. None
produced an error. This PR adds tests that specifically check the **loud failure** path:

- CHAID binning all metrics to "Unknown" triggers an assertion, not a report with "Unknown" bins.
- A registry key mismatch raises, not silently skips the module.
- An L0 trim that removes everything raises, not returns an empty report.
- A guard truncation that hits the hard limit raises, not submits a truncated prompt.

The commit message names the pattern: "This codebase's characteristic defect is not a
crash, it is a believable result." These tests do not verify correct output. They verify
that breakage is audible.

### PR #18 - Risk edit was broken in production; test hid it

`RiskPage` called `PUT /risks/{id}`. The API serves `PATCH /risks/{risk_id}`.

The MSW mock matched `PUT` (the wrong method), so every frontend test passed. Against the
real API the call returned 405. Risk editing was broken in production and worked in every
development environment.

Fixed both: `PATCH` in `RiskPage`, `PATCH` in the mock. The mock now fails the test if
the method does not match the API spec.

### PR #19 - ORM/migration column drift detection

`test_migrated_schema_matches_orm_tables` compared which **tables** exist. It passed even
when an ORM model gained a column that no migration added - which is exactly how the
confidence and completeness columns produced two production bugs earlier this month.

Extended: the test now diffs columns per table against the live migrated schema. A model
column without a migration fails the suite at commit time.

### PR #21 - DATA_CONTRACTS.md: the month in one document

The August audit produced one structural finding: **every defect lived at a boundary
between components, not inside either one.** The scripts worked. The registry was valid
JSON. The frontend was well-formed. The mock was a working mock. The models and migrations
were each internally correct. The agreements between them were broken.

`docs/architecture/DATA_CONTRACTS.md` names each contract, the exact form each side expects, and the
test or CI check that now enforces it:

| Contract | Failure mode observed | Now enforced by |
|---|---|---|
| `output_file_patterns` key format | 7 modules silently skipped | `test_registry_output_contract.py` |
| Frontend method vs API method | 405 in prod, passing mock in dev | PR #18 mock fix |
| ORM column vs migration column | Null score, broken confidence | PR #19 column drift test |
| module\_id format vs `CODE_RE` | Labels silently dropped | `test_labeling.py` |
| L0 trim threshold vs guard limit | 4.8x over limit, truncated report | `test_trim_coverage.py` |

`HOW_IT_WORKS.md` corrected: it still described the single-module architecture.

The module root is now clean: `ESGRC/`, `RUNBOOK.md`, `docker-compose*.yml`, etc.

Two things surfaced during the refactor:

1. **Combined-suite pytest bug (new, not pre-existing).** Running both suites in a single
   `pytest` invocation causes 4 failures in `test_rate_limits.py`. The rate limiter binds
   its Redis storage at import time from `REDIS_URL`; `pipeline/test/conftest.py` sets
   that variable, so when both suites share a process the ESGRC rate-limit tests get a
   Redis URL nobody started and fail. Running each suite separately (as CI and
   `run-tests.ps1` do) works fine. Fixed: path globs in the generator + 4 test files;
   the underlying import-time binding is noted but intentionally left alone (it is
   correct behaviour for a prod process, just unfortunate in a shared test process).

2. Eleven test failures caught by the existing suite because path globs still pointed
   to the old module locations. `test_dockerfile_copies_the_modules_analytics_scripts`
   caught all 11. Fixed in the same PR.

## Note on the day

errors. Today's three production bugs (registry keys, risk edit 405, Playwright never
running) are the same pattern from different angles: things that look correct and are not.

finding individual instances of it. Every contract in that table is now enforced; a new
module or endpoint that breaks a contract fails CI at commit time.

where contracts are hard to verify. With the module wall gone, the structure is what it
