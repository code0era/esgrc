### Secrets

- **A live-format Anthropic key was sitting in `ESGRC/.env.example:36`** - the
  same key as the working one in the gitignored `.env`. Not in git history
  (checked with `git log -S`), hidden from view only because `ESGRC/.gitignore`
  has `.env.*`, which also covers `.env.example`. Replaced with a placeholder.
  **The key must still be rotated** - it was on disk in the file people are told
  to copy.
- `.dockerignore` used bare `*.db` / `.env`, which match only the context root.
  `COPY ESGRC/ /app/` was therefore baking `ESGRC/.env` (real `SECRET_KEY`) and
  the 303 KB dev `esgrc.db` into image layers. Now `**/`-prefixed. Verified with
  a real `docker build`: of the probe files, only `ESGRC/main.py` survives.

### Multi-tenancy defect (new, not previously known)

- `esg_categories` and `compliance_frameworks` still carried the single-column
  `UNIQUE(name)` from the pre-tenancy initial schema. The tenancy migrations only
  *added* the composite `uq_*_org_name`; nothing dropped the original, and SQLite
  batch mode faithfully reproduced it on every rebuild.
- Effect: **two organisations could not both have a category or framework of the
  same name.** Org B creating "GRI Standards" got an IntegrityError that
  `crud.py` reported as "already exists in your organisation" - misleading, and
  it leaks that another tenant holds the name.
- Reproduced on a real migrated DB before fixing, then fixed via
  `20260805_drop_global_uniques` (dialect-aware: discovers and drops the
  auto-named constraint on Postgres, rebuilds the table via `copy_from` on
  SQLite, since the constraint is unnamed there and cannot be dropped by name).
- Root cause of the blind spot: **conftest builds its schema with `create_all`
  from the models, not by running migrations**, so no test ever saw the migrated
  schema. Added `ESGRC/test/test_migrated_schema.py`, which runs the real chain
  into a throwaway DB. Confirmed it fails without the migration (2 failures) and
  passes with it.

### Auth

- `REFRESH_TOKEN_EXPIRE_DAYS` was configured but never read anywhere: tokens
  carry no timestamp and rotation only compared hashes, so **a stolen refresh
  token was valid indefinitely**. Added `users.refresh_token_expires_at`
  (migration `20260805_refresh_expiry`), stamped on issue and enforced on use.
  Pre-existing sessions have NULL and fail closed - one extra login, no
  credential outlives the policy.

### Duplicate scheduler

- The API runs `uvicorn --workers 2` and every worker executes the FastAPI
  lifespan, so **both workers built an APScheduler over the same jobstore and
  both fired the daily and compliance batches** (`max_instances=1` is per
  scheduler, not global). The two workers also raced `alembic upgrade head`.
- Added `app/services/single_instance.py` (OS file locks): the scheduler is
  claimed by one worker, and the startup migration is serialised so the first
  worker migrates while the rest wait. Verified the POSIX `fcntl` branch inside
  a Linux container, since local tests only exercise the Windows branch.
- Caveat recorded in code: this coordinates processes on one host, not multiple
  API containers. Scaling `api` past one replica needs the scheduler split out.

### LLM client (three bugs)

- **Model upgrade read the wrong number.** The Haiku→Sonnet check used
  `check_result.token_count`, which is the count *after* the guard truncated,
  instead of `original_token_count`. On content lighter than the assumed
  chars-per-token ratio a ~180K-token report truncates to ~125K, the upgrade
  never fires, and Haiku silently gets a middle-cut report that Sonnet 4.6 could
  have taken whole.
- **`NOW()` in raw SQL** is Postgres-only, so every Claude persistence raised
  "no such function: NOW" on the SQLite demo path. Now a bound datetime, matching
  every other raw-SQL write in the codebase.
- **`prompt_id` was accepted and dropped** - in neither the column list nor the
  params - so every row written since `20260622_add_prompt_id` had NULL, and no
  output could be traced to the prompt version that produced it.
- Added `pipeline/test/test_llm_persistence.py`. Confirmed 3 of 4 fail against
  the pre-fix code.

### Analytics

- **CHAID segmentation was computed from placeholders.** `bin_features` was
  called with `trends` / `repetitions` / `dep_inc` / `ind_inc` left over from the
  last iteration of the dataset loops (Sub_Modules) while being paired with the
  *metric* correlation matrix, so every lookup missed and every metric was binned
  as "Unknown" / "Insufficient" / zero inconsistencies. Fixed in all four
  modules; proved with a harness that the old wiring yields only `Unknown` and
  the new one carries real values through.
- **Seeded the scenario simulation** (`ANALYTICS_SEED`, default 42) in all four
  module regressions and L0, so the client-facing "risk drivers" ranking stops
  changing on every run of identical data.
- **Low-performer rankings used `.iloc[0]`** - one arbitrary row out of ~3000,
  and there is no date/period column in the input to make row 0 meaningful. Now
  the mean across the series. **This changes reported numbers and needs
  Praveen's sign-off** (see NEXT).
- **L0 weights were reported but never applied.** The keys are metric IDs
  (`INM10101`) while `compute_overall_risk` iterates sub-module columns
  (`XXX10000`), so nothing matched, everything defaulted to 1.0, and the report
  still printed "Weights applied in this run". Now splits matched from unmatched,
  warns loudly, and the report says which were not applied.

### Frontend

- **Every page refresh logged the user out.** The access token is memory-only by
  design and nothing spent the surviving httpOnly refresh cookie at boot. Added
  `src/lib/session.ts` + a restore gate in `App.tsx`. The once-only guard is
  load-bearing: refresh tokens are single-use and rotate, and StrictMode
  double-invokes effects, so an unguarded call would look like a replayed token
  and log the developer out on every load.
- **The 401 interceptor treated `/auth/me` and `/auth/users` as unrefreshable**
  because it matched on `/auth/` wholesale. An admin on Settings > Users past the
  30-minute token lifetime was bounced to login while holding a valid cookie.
  Now an explicit list of login/register/refresh/logout.
- **Queued requests leaked on refresh failure**: `waiters = []` discarded the
  resolvers without rejecting, so those promises never settled. Now rejected.

### Tests

- Added `pipeline/test/test_chain_composition.py` - nothing previously executed
  `build_apex_pipeline`, `build_esgrc_chain` or the factory builder, so the
  canvas most likely to break against a real broker had zero coverage.
  **Result: the Apex nested chord composes fine**, which settles the open
  question about the `group(chain, chain)` shape.
- That test exposed a real latent fragility: `test_apex_e2e` / `test_esgrc_e2e`
  patch `pipeline.tasks.r2.*`, which only reaches the chain modules if they have
  not been imported yet, so those tests silently depended on collection order.
  Fixed by also patching each chain module's own bindings, the pattern
  `test_apex_e2e` already documents for its later tests.
