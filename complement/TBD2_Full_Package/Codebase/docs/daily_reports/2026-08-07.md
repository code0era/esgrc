### The find of the day: Apex was about to lose 79% of its report

The top-N report trim exists in all four module-level correlation scripts. **It was never
applied to the L0 roll-up.** That did not matter while Apex rolled up three modules: the
4 Aug live run sent 75,515 tokens. Adding seven modules changed it.

Measured by running the full L0 chain against all 12 module handoffs:

| Report | Bytes | Share |
|---|---:|---:|
| `inconsistency_report_L0.txt` | 1,343,162 | 67% |
| `correlation_analysis_L0.txt` | 617,972 | 31% |
| everything else | 37,885 | 2% |
| **TOTAL** | **1,999,019** | **~909,000 tokens** |

The hard limit is **190,000**, so **4.8x over**. The guard would have truncated roughly four
fifths of the enterprise report before Claude saw it. Both offending reports scale with the
**square** of the column count, which is why it only surfaced once enough modules existed.

Nobody would have caught this from outside. The run completes, Apex produces a report, and it
is simply vague, exactly as ESGRC's was before its own trim.

Fixed: **1,999,019 → 40,709 bytes, ~909,000 → ~18,504 tokens, 49x, now a tenth of the limit.**
Verified it touches only the write path by running the chain before and after against the same
12 handoffs: `chaid_risk_segmentation_L0.txt` and `trends_and_repetitions_report_L0.txt` are
byte-identical apart from their timestamp.

Worth recording what was being discarded: of **14,365** enterprise pairs, exactly **3** clear
|r| >= 0.5, mean |r| **0.0181**. The 617 KB matrix was almost entirely near-zero correlations.
So Claude now gets the three that matter plus summary statistics, rather than those three
buried in 14,362 that carry no signal.

A new test sweeps **every** module's correlation script for the trim, so a future generated
module cannot miss it the way L0 did.

## Note on process

Three of today's findings came from the same place: **a defect that produces output instead of
an error.** The L0 truncation would have produced a complete-looking enterprise report. Brand's
`EBM` would have silently dropped a module from the roll-up. The Co-Pilot TTL sat at 7 days
because the value was inlined where nobody read it.

That is the same pattern as every analytics defect found this week, and the reason I keep
asking for the canary checks. They change no number; they only stop a broken run from writing
a report that looks fine.

PowerShell's `-Encoding utf8` added a BOM, and the analytics scripts call `open()` with no
encoding, so `json.load` died on character 0. Caught by running the module rather than
trusting the edit, then audited all 11 vendored JSONs to confirm none carries one.
